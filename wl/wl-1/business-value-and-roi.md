# Business value, alternatives and ROI case for wiselotus

Status: draft research note, 2026-11-14. Scope: what each persona gains from wiselotus versus not having it, how it compares with other ways of putting knowledge into agent context, what published productivity evidence exists, and how to justify the investment.

**How to read the evidence labels.** Every study is tagged **independent** (academic or third-party, not selling the tool) or **vendor-reported** (published by the seller or a close partner). Figures are quoted only as stated in the cited source. Anything I could not confirm against a primary source is marked **Unverified**. Nothing in this note is a measured wiselotus result: wiselotus has no code or deployment yet (the repository has no `python/` or `kotlin/` directory as of 2026-11-14), so all benefits below are **hypotheses to test**, not findings.

## 1. Summary

- The strongest evidence that bears on wiselotus is not about review memory itself. It is about context: more tokens do not reliably help (Lost in the Middle, Context Rot), and repository context files do not generally improve coding-agent task success while raising inference cost (arXiv:2602.11988v3). That supports wiselotus rule 3 (precision over recall, small slices).
- Published productivity evidence on AI coding tools is mixed. One vendor-partnered controlled experiment reports a 55.8% speedup, one independent trial on experienced maintainers reports a 19% slowdown, and a Google DORA survey links AI adoption to lower delivery stability. No source I found measures review-history memory serving specifically. **No independent controlled study of review-lesson serving was found.**
- The honest ROI case is therefore: wiselotus is cheap to measure (it has built-in outcome metrics) and should be justified by a pilot that reports those metrics, not by borrowed productivity percentages.

## 2. Benefit per persona: with wiselotus versus without

Persona set follows the task brief (developer, reviewer or tech lead, platform team, engineering leader, compliance owner). If the T1 persona note differs, align the names there. All "with" cells are hypotheses.

| Persona | Without wiselotus | With wiselotus (hypothesis) | What would prove it |
|---|---|---|---|
| Developer | Learns team expectations by having review comments repeated on each MR, or by reading a static rules file that may be stale. The agent generating code does not know them. | The agent receives a small, scoped slice of expectations with links to the review events behind them, at generation time. | Fewer repeat review comments per MR on covered scopes; slice `helped` outcomes. |
| Reviewer or tech lead | Re-writes the same comment many times; expectations live in heads and old threads. | A recurring comment becomes a lesson once and is served before the next MR. Judgment stays human. | Share of review comments matching an existing lesson; reviewer time per MR (measure, do not assume). |
| Platform team | Maintains rules files per repo and per harness; each vendor tool has its own memory. | One lesson graph, served through an MCP tool and a CLI with one contract (rule 9). | Harnesses served per lesson store; effort to onboard a new repo. |
| Engineering leader | Cannot see which guidance helps; adoption of AI tools is judged by surveys and anecdote. | Aggregate outcome data (`helped`, `ignored`, `misled`) and token cost per slice, with no per-person ranking (rule 6). | Misled rate trend; tokens per slice; cost per 100 review events. |
| Compliance owner | Review text may carry secrets or personal data and may be copied into prompts or vendor memory without clear controls. | Redaction at ingest, evidence-linked lessons, read-only toward sources, content treated as data (rules 1, 2, 5, 8). | Redaction test pass rate; audit trail from any served lesson to its evidence. |

Caveat: the "without" column describes common patterns documented in vendor docs below, not a measured baseline for any specific organisation.

### 3.2 Approach notes

#### Static instruction files

arXiv:2602.11988v3 (independent per this note's labels, author affiliations not checked; v1 February 2026, v3 revised 29 September 2026) evaluates repository-level context files for coding agents. The v3 abstract reports that context files "do not generally improve task success rates" while increasing inference cost by over 20% on average. In v3, versus no context, developer-written files improved resolution by about 2.4% (p = 0.21) and LLM-generated files lowered it by about 2% on CTXbench (p = 0.37; about 0.5% on SWE-bench, p = 0.87), neither significant, while developer-written files beat LLM-generated ones by 7% (p = 0.038). The over-20% cost rise is an average: developer-written files raised cost by at most 19% (v3), and v1 section 4.2 reports average rises of 20% and 23% for LLM-generated files on its two benchmarks. The v1 abstract said context files "tend to reduce task success rates"; later versions softened this, so cite the version. v3 renames the developer-written benchmark from AGENTbench to CTXbench. Takeaway for wiselotus: keep static files short and human-written, and use wiselotus for the changing, evidence-backed part. Note this paper tests repository context in general, not review lessons.

#### Retrieval over docs or code

Ovadia et al. (arXiv 2312.05934, Microsoft authors, academic preprint) compare fine-tuning with RAG for knowledge injection and report RAG consistently outperforming unsupervised fine-tuning. RAG answers "what do the docs say" but review expectations are often not in docs. wiselotus can be seen as retrieval over a curated, evidence-linked lesson store rather than over raw text.

#### Long-context stuffing

Liu et al. (arXiv 2307.03172, independent) report best performance when relevant information is at the start or end of the context, lower in the middle, and falling performance as input grows, even for long-context models. Chroma's Context Rot report (July 2025, a vendor of retrieval tooling, so treat as vendor-reported) reports reliability declining as input length grows across the models it tested. Prompt caching reduces the price of repeated prefixes (Anthropic docs list cache writes at 1.25x the base input price for a 5-minute TTL or 2x for a 1-hour TTL, and cache reads at 0.1x for most models, with lower read multipliers for some newer models), but it does not fix the accuracy findings above.

#### Fine-tuning

Per arXiv 2312.05934, fine-tuning gave some improvement but RAG outperformed it, and the abstract notes models struggle to learn new facts through unsupervised fine-tuning. Review expectations change often, which makes weights a poor store (design reasoning, not a cited finding).

#### Vendor review-tool memory

CodeRabbit documents "learnings" as natural-language notes created from replies in pull requests or imported from files, which can be reviewed and edited. Only users with the CodeRabbit Admin role can edit or delete stored learnings in the dashboard, and admins can approve or reject pending learnings; learnings created from an open pull request apply first to that pull request and become repository-wide after merge (CodeRabbit Cloud only). The same page also says any user can request changes to learnings through comments, Enterprise teams can update or delete them through the API, and pending chat-sourced learnings are applied automatically after a configurable approval_delay (0 to 30 days, default 0, meaning immediately) unless an admin rejects them first, so admin review is optional rather than a hard gate. Greptile documents learning from reactions and engineer comments. Its best-practices page advises "Give the learning system 2-3 weeks to adapt to your reactions", and its memory page shows an illustrative timeline from week 1-2 (standard suggestions, high noise) to week 9+ (highly personalized). **Unverified:** Greptile admin controls over learned rules (not shown on either page). Both are vendor documentation, so benefit claims are vendor-reported. I found third-party comparison pages with precision figures for these tools, but they were internally inconsistent, so I do not use them. **Unverified:** precision of either tool's memory. The lock-in rating is a design judgment: memory lives inside each vendor product.

## 4. Published ROI and productivity evidence

All rows are quoted from the cited source. None studies review-lesson serving, so they bound the plausible effect of AI assistance in general and do not predict wiselotus results.

| Study | Label | Design | Figure stated in the source | Relevance |
|---|---|---|---|---|
| Peng et al., "The Impact of AI on Developer Productivity: Evidence from GitHub Copilot" (arXiv 2302.06590) | Vendor-reported (authors from Microsoft Research and GitHub, with MIT Sloan) | Controlled experiment, implement an HTTP server in JavaScript | Treatment group completed the task 55.8% faster | Single, isolated task; not review or maintenance work |
| GitHub and Accenture enterprise research (GitHub blog) | Vendor-reported | Randomized controlled trial per GitHub's write-up | 15% increase in pull request merge rate; 8.69% increase in pull requests; 84% increase in successful builds | Shows a review-adjacent metric. Figures confirmed on the GitHub blog; sample size and statistics are not stated there. **Unverified** (sample size and statistics only) |
| METR, "Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity" (arXiv 2507.09089) | Independent | Randomized trial, 16 developers, 246 tasks, mature repositories | Allowing AI increased completion time by 19%; developers forecast a 24% speedup and afterward estimated a 20% speedup | **Counter-evidence.** Authors caution against overgeneralizing and note possible learning effects |
| Google DORA 2024 report | Survey research by Google Cloud (a vendor of AI coding tools) | Survey-based estimates | Per the Google Cloud blog: as AI adoption increased, an estimated 1.5% decrease in delivery throughput and 7.2% reduction in delivery stability (RedMonk's coverage frames both per 25% increase in AI adoption); per 25% increase in AI adoption, a 3.4% increase in code quality and a 3.1% increase in code review speed | **Counter-evidence** on stability. Correlational. The report PDF could not be fetched (over 10 MB), so report page numbers are **Unverified** |
| arXiv:2602.11988v3, AGENTS.md evaluation | Independent (author affiliations not checked) | Benchmarks (SWE-bench and CTXbench, called AGENTbench in v1) | Context files do not generally improve task success (developer-written about +2.4%, p = 0.21; LLM-generated about -2% on CTXbench, p = 0.37 (about -0.5% on SWE-bench, p = 0.87); developer-written beat LLM-generated by 7%, p = 0.038) and raise inference cost by over 20% on average | **Counter-evidence** to loading unfiltered context; supports small, curated slices |

Reading across rows:

- **Perception gap.** METR found developers believed AI helped while measured time rose. Any wiselotus pilot must measure outcomes, not rely on satisfaction surveys.
- **Task type matters.** The 55.8% result is for a greenfield task, the 19% slowdown is for experienced maintainers in familiar repositories. wiselotus targets the second setting, so the faster-task figure should not be used as its baseline.
- **Not found:** an independent, controlled study of review-history memory or lesson serving for coding agents. Vendor docs describe the feature but I found no verified outcome numbers.

## 5. Investment justification framework

### 5.1 Cost drivers

- **Ingest and extraction model calls**, driven by review event volume (tracked as cost per 100 review events).
- **Serving tokens**, driven by slice size and the number of generation events (tracked as tokens per slice).
- **Engineering build and run**: two languages, schemas, MCP and CLI surfaces (see decision records for language choices).
- **Curation and review time** for lessons that need a human check.
- **Security and compliance work**: redaction testing, retention review, approvals for any new dependency or source.
- **Opportunity cost** of the pilot repos and reviewers.

### 5.2 Leading indicators mapped to tracked metrics

| Indicator | wiselotus metric (`AGENTS.md`) | Why it leads value | Direction wanted |
|---|---|---|---|
| Fraction of extracted lessons a reviewer confirms as correct | Lesson precision | Wrong lessons cost more than missing ones (rule 3) | Up |
| Fraction of the top k served lessons that were relevant | Slice precision@k | Measures whether the slice is worth its tokens | Up |
| Share of served lessons with `misled` outcomes | Misled rate | Direct harm signal; drives decay and retirement (rule 4) | Down |
| Tokens added to each generation event | Tokens per slice | Cost and context-rot exposure | Down, within the 2k default |
| Spend per 100 ingested review events | Cost per 100 review events | Running cost of the learning loop | Down or stable |

Lagging outcomes to pair with them (measured by the organisation, not by wiselotus): repeat review comments per MR on covered scopes, review cycles per MR, time to merge, and change failure indicators. Given the METR perception gap, capture these from systems of record.

### 5.3 Template ROI calculation

Every input below is an **assumption you supply**. This note does not provide values and none should be read as data. The interactive calculator in the HTML view implements the same formula with empty fields.

Benefit per period = (MRs per period) x (repeat comments avoided per covered MR, A1) x (minutes per comment, A2) / 60 x (loaded cost per hour, A3) x (share of MRs in covered scopes, A4)

plus optional terms you may add and must justify: avoided rework from `misled` or defect reductions (A5), reduced onboarding time (A6).

A1 is measured on covered MRs only, so multiplying by A4 does not discount twice.

Recurring cost per period = (review events per period / 100) x (cost per 100 review events) + (generation events per period) x (tokens per slice) x (price per token) + (run effort hours per period) x (loaded cost per hour) + (curation hours per period) x (loaded cost per hour) + (other recurring costs, A7)

One-off build cost = (build effort hours) x (loaded cost per hour) + (one-off other costs). It is not part of the recurring cost, so it is not counted twice.

ROI per period = (Benefit - Recurring cost) / Recurring cost. Payback (in periods; months if the period is a month) = (one-off build cost) / (Benefit per period - Recurring cost per period). If Benefit per period - Recurring cost per period is 0 or less, payback is none.

Assumption register to fill in:

| ID | Assumption | Source for your value (must be your own data or a cited study) |
|---|---|---|
| A1 | Repeat review comments avoided per covered MR | Pilot measurement against a control set of repos |
| A2 | Minutes spent per review comment, both sides | Your review tooling or a time sample |
| A3 | Loaded cost per engineering hour | Finance |
| A4 | Share of MRs touching scopes that have lessons | Coverage report from the lesson graph |
| A5 | Avoided rework per prevented defect | Incident or defect cost data |
| A6 | Onboarding time saved | HR or team data, **Unverified** until measured |
| A7 | Other recurring costs (security review, licences) | Your estimate |

Sensitivity guidance: vary A1 and A4 first, because they are the least known; run the low case with A1 near zero to see whether the cost side alone is acceptable. Because AI assistance has shown both gains and slowdowns (section 4), do not offset costs with a generic productivity percentage.

### 5.4 Suggested pilot design

1. Pick matched repos; serve slices in some, none in others (or alternate by week).
2. Record the five wiselotus metrics weekly plus the lagging outcomes above.
3. Set stop rules before starting: for example, retire the pilot if the misled rate stays above a threshold you set.
4. Report with the evidence labels used in this note.

## 6. Risks and open questions

- Benefits depend on review history volume; small teams may have too few events (**Unverified**, no data).
- Review text can contain instruction-shaped content, handled by rule 1; a security test is part of the cost.
- Vendor tools may close the gap with their own memory; the differentiator is portability and governance, to be confirmed with users.
- Next steps: confirm persona names with T1, align with the T2 landscape note, and let T4 fold this into the synthesis.
