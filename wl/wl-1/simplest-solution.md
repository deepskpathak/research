## 1. The problem in one line

Review knowledge is trapped in closed threads, agents repeat flagged mistakes, and hand-written instruction files only hold what someone remembered to write (see [personas-and-problem.md](personas-and-problem.md)). Repeated-comment frequency is **Unverified**: no fetched source quantifies it.

## 2. Evidence that shapes the design

- **Fact:** model performance degrades as input length grows [2] (vendor research, Chroma Technical Report, 14 July 2025; it found no notable variation by needle position). Separately, relevant information in the middle of a long input is used worse [1]. **Fact:** for repository context files, neither type significantly changes task success; inference cost rises by over 20% [3] (arXiv:2602.11988v3: developer-written about +2.4%, p=0.21; LLM-generated about -2% on CTXbench, p=0.37 (about -0.5% on SWE-bench, p=0.87); developer-written beat LLM-generated by 7%, p=0.038). The v1 abstract said context files "tend to reduce" task success. Source: [business-value-and-roi.md](business-value-and-roi.md).
- **Fact:** hand-written instruction files are common (2,303 files in 1,925 repos studied) but their effect on agent quality was not measured there [4]. Source: [landscape-and-patterns.md](landscape-and-patterns.md).
- **Fact:** Claude Code loads only the first 200 lines or 25KB of its auto memory, so a hard load budget is already normal in a shipping harness [5] (vendor docs, no results reported).
- **Fact:** CodeRabbit and Greptile learn review preferences from feedback, per vendor docs only [6][7]. CodeRabbit already records metadata such as the pull request number, filename and user with a learning [6], so traceability alone is not new. A traceable, outcome-weighted lesson graph under a small budget is not described on the fetched pages. Novelty is provisional.
- **Fact:** MCP is an open protocol with named client adoption, but no quality results [8].
- **Fact:** productivity evidence on AI coding tools is mixed (a 55.8% speedup in one vendor-partnered experiment [9], a 19% slowdown in one independent trial [10]). No independent study of review-lesson serving was found.

## 3. Recommended design (all Recommendations)

**Recommendation:** build the smallest thing that is deterministic end to end, and put the model at exactly one step.

1. **Lesson store: append-only JSONL plus versioned JSON schema.** One lesson per record: text (one or two sentences), scope, evidence links, confidence, state. No graph database at first. The "graph" is just lessons linked to evidence ids and to each other by `supersedes`. State files are written to a temp file and renamed (existing `AGENTS.md` rule).
2. **Redact at ingest.** Secrets and personal data are removed before anything is stored. Excerpts are short. Reviewer identity never enters a lesson.
3. **One model step: extraction.** A candidate lesson is proposed from events through the provider adapter. Dedupe, normalization and evidence checking are code. No evidence, drop.
4. **Scope matching in code.** A slice request carries repo, paths, symbols, language, change type. Lessons match by exact or glob scope. No embeddings in v1.
5. **Ranking in code.** Score = confidence, then recency, then evidence count. Fill a token budget (default 2k) greedily and stop. An empty slice is valid.
6. **Serve one contract two ways.** One function, `get_slice(request) -> slice`, exposed as an MCP tool and a CLI command with identical JSON. Lessons are rendered quoted with provenance, instruction-shaped text stripped.
7. **Outcome feedback.** After a slice, record `helped`, `ignored` or `misled`. Confidence is a plain function of outcome counts, recency decay and evidence count. Misled lessons decay and retire.
8. **Measure first.** `make eval` reports lesson precision, slice precision@k, misled rate and tokens per slice before any claim of benefit.

Why this is simple: eight components, one model call site, no vector store, no agent-managed memory, no write access to sources.

## 4. Patterns adopted and rejected

Patterns are from the pattern table in [landscape-and-patterns.md](landscape-and-patterns.md).

### Adopted

| Pattern | Reason (evidence, then recommendation) |
|---|---|
| Hand-written instruction files as a delivery format [4] | **Fact:** widely used. **Recommendation:** render slices into them as an optional output, so wiselotus fits existing harnesses. |
| Hard load budget [1][2][3][5] | **Fact:** position and length effects [1][2], no reliable gain from context files plus extra cost [3], vendor guidance to keep files short [5]. **Recommendation:** fixed 2k slice, precision over recall. |
| Feedback-learned preferences [6][7] | **Fact:** peers do this (vendor docs). **Recommendation:** adopt the idea, add mandatory evidence links and outcome-driven confidence as the difference. |
| Reflection loop at lesson level [11] | **Fact:** Reflexion reports 91% HumanEval pass@1 versus 80%, authors' own evaluation, not review work. **Recommendation:** use only the shape (feedback signal adjusts what is kept), not the claimed gain. |
| Skill library plus self-verification [12] | **Fact:** Voyager keeps a skill library plus a self-verification step, in Minecraft only. **Recommendation:** keep the idea of a durable lesson set that is checked before it is kept. Transfer to review is **Unverified**. |
| Applied suggestion as outcome signal [13] | **Fact:** Google reports 40% to 50% of previewed edits applied (self-reported). These are ML-generated edits that code authors applied, not human reviewer suggestions. **Recommendation:** treat "suggestion applied" as a cheap `helped` signal; the Google figure supports this only by analogy. |
| MCP plus CLI [8] | **Recommendation:** AGENTS.md rule 9. MCP gives harness reach, CLI gives scripting and tests. |
| Public datasets for fixtures [14] | **Fact:** the CodeReviewer Zenodo record lists Creative Commons Attribution 4.0 International [19]. Whether that covers the underlying repository content, and so license compatibility for wiselotus, is **Unverified**. **Recommendation:** seed fixtures and evals from public review data once license compatibility is confirmed, then measure on wiselotus's own data. |

### Rejected (for v1)

| Pattern | Reason |
|---|---|
| Tiered virtual context managed by the system, per abstract (MemGPT/Letta [15]) | **Recommendation:** heavier than needed and non-deterministic. A fixed budget served by code is simpler to test and audit. Its benefit is **Unverified** for review lessons. |
| LLM memory consolidation at serve time (Mem0 [16]) | **Fact:** its headline numbers are self-reported and conversational [16], and its README says the scores reflect the managed platform, which includes proprietary optimizations not available in the open-source SDK [18]. **Recommendation:** keep the model out of the serve path. |
| Agent-written memory from corrections [5] | **Fact [5]:** Claude does not save something every session. **Recommendation:** no per-entry provenance is described on the fetched page, which conflicts with rule 2. |
| Embedding retrieval over raw review history (RAG [17]) | **Recommendation:** defer. Exact scope matching is auditable and cheap. Add embeddings only if evals show scope matching misses relevant lessons. |
| Open-PR learnings promoted repository-wide on merge [6] | **Fact:** CodeRabbit learnings from an open PR first apply only to that PR, then become repository-wide after merge [6]. **Recommendation:** keep the merge gate in spirit (durable lessons need evidence from resolved reviews), but reject promotion on merge alone: a wiselotus lesson also needs mandatory evidence links, and its confidence moves with served outcomes, so a merged but misleading lesson decays and retires. |
| Auto-commenting or editing source repos | **Recommendation:** out of scope (rule 8, read-only). |
| Per-reviewer weighting | **Recommendation:** forbidden by rule 6. Confidence never comes from the author. |

## 5. Persona to value

Values below are design intent. Measures are proposals, not study results. Detail in [personas-and-problem.md](personas-and-problem.md) and [business-value-and-roi.md](business-value-and-roi.md).

| Persona | Value from the minimal design | Measure to report |
|---|---|---|
| Developer using an agent harness | First drafts reflect repo-specific review expectations, without maintaining a file by hand. | Repeat-lesson comments per change, `helped` vs `misled` counts. |
| Reviewer or tech lead | Fewer restated comments, review time kept for design and risk. | Share of comments that restate a lesson. |
| Platform or DevEx team | One contract (MCP and CLI) across harnesses. | Harnesses served, tokens per slice, retired stale lessons. |
| Engineering leader | A pilot with built-in metrics instead of borrowed productivity percentages, given mixed external evidence [9][10]. | Aggregate misled rate, cost per 100 review events. Never per person. |
| Security or compliance owner | Redaction at ingest, read-only toward sources, evidence audit trail for each served lesson. | Zero secrets in excerpts, 100% lessons with evidence. |

## 6. Open questions

- Does serving lessons reduce repeated comments or agent errors? No independent study found. Needs the repo's own evals.
- Is scope matching without embeddings enough? Test by measuring missed relevant lessons.
- How should confidence combine outcomes, recency and evidence count? Start with a simple documented formula and tune on fixtures.
- Is there enough review history in a small team? **Unverified**.
- Which personas are real buyers? Needs interviews. **Unverified**.
- Not covered by the research: Cursor rules. Qodo Merge learning was not studied in depth; the Qodo v1 docs describe monthly auto best practices generated from accepted suggestions, and v1 is being sunset [20].

## 7. What to build first (Recommendation)

1. Schemas in `schemas/` for event, lesson, slice, outcome, with a shared fixture (needs a contract test on both sides).
2. Ingest from fixture review events with redaction, writing append-only JSONL.
3. Extraction through the fake provider, evidence check, dedupe.
4. Scope matching and ranking with a token budget, as a pure function with tests.
5. CLI `slice` command, then the MCP tool over the same function.
6. Outcome recording and the confidence function.
7. `make eval` metrics on fixtures, then a pilot on one real repo before any ROI claim. Per ADR practice, record the language choice per component in `docs/decisions/` first.
