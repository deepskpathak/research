## Problems

The agents are not uninformed. Claude Code reaches EngHub over MCP, Devin has its knowledge bases, and both can load certified and local skills. The problem is that what an agent knows on any given task depends on which harness the developer chose, which skills they happened to install, and what they pasted into the session. Firm knowledge reaches agents through channels that are uneven across harnesses, assembled by hand, unmeasured, and stale on the next release. Each of the six problems below carries a cost the firm is already paying.

1. *Firm conventions reach agents unevenly, and the gaps surface in review.* A developer asks an agent to add a retry wrapper around an internal service call. In Devin, a knowledge base entry may steer it to the firm's approved resilience library. In Claude Code, the answer is available if the developer installed the right skill or the EngHub page is indexed. In Copilot, and in Codex once adopted, the agent has nothing beyond what sits in the repository. The output compiles and passes tests in all four cases. Whether it also uses a banned dependency, a deprecated API pattern, or the wrong logging convention is decided by harness choice, not by the rule. The rule existed; the agent may or may not have seen it.

   *Cost: senior review time and rework cycles.* Rejections for firm-knowledge reasons land on the engineers who know the conventions, which is the most expensive labor in the organization, spent catching errors an agent could have avoided. Each rejection is a second agent run, a second review, and a delay to whatever the developer was trying to ship.

2. *Reachability depends on the harness, and even reachable sources must be pointed at.* Documentation, Jira, Confluence, the code graph, and skills are each reachable from some harnesses and not others. Claude reaches Jira and Confluence through skills over S2SProxy; Devin reaches them only through what someone copied into a knowledge base; Copilot reaches them through skills if a team built them; Codex reaches none of it. Where a source is reachable, the agent still has to be told which source answers which question. An agent deciding whether a library version is approved will not consult the Confluence approval page unless something in its context names that page as the authority.

   *Cost: duplicate integration effort, rebuilt on every harness change.* Every per-team connection is engineering time spent on a problem the firm has already solved elsewhere. The Copilot deprecation makes this concrete: integrations built for it are being retired, and the same integrations will be built again for Codex.

3. *The workaround for problems 1 and 2 is to front-load everything, which bloats the context window.* With no service to fetch the right guidance at the right moment, developers compensate by loading guidance up front. Instruction files (CLAUDE.md, AGENTS.md, copilot-instructions.md) grow by accretion as each review rejection adds a rule and nothing removes one. Teams commit full coding standards into repositories, auto-load a dozen skills at session start, and paste Confluence pages into the prompt. Every rule in that payload is sent on every request, whether or not the task touches it. The consequences are mechanical: the model spends attention on irrelevant rules, follows some of them too literally, and carries forward guidance that has since changed. Independent research on agent instruction files has found that large, poorly curated instruction files can reduce task success rather than improve it. The instinct to add more context is reasonable; the outcome is an agent that is slower and more expensive without being more correct.

   *Cost: token and compute spend, paid on every call.* A team that loads a large instruction file into every session pays a tax on every request. The tax scales with the number of agents, the number of sessions, and the size of the file, and none of those are trending down.

4. *Each team runs its own knowledge supply chain.* Ask how a given team gets firm context into its agents today and the answers vary: a per-team skills registry maintained by one engineer; a scraper against Jira or Confluence running under a system token; a Devin knowledge base curated by whoever set it up; a shared wiki page of prompt snippets; and, most commonly, an individual developer sourcing and pasting what they think the agent needs. The same problem is being solved independently across teams, with different data quality each time.

   *Cost: ungoverned reach.* Where retrieval is bespoke, so are access control, provenance, and audit. A scraper under a system token does not carry the requesting developer's entitlements. A pasted page carries no record of where it came from or whether the developer was permitted to see it. Each bespoke path is a new conversation with Tech Risk, and each one is had from scratch.

5. *Nothing is measured.* The firm does not know, per product or per team, how often agent output is rejected for a firm-knowledge reason versus a logic reason. It does not know which sources agents consult, which rules in an instruction file are ever relevant, or what share of context tokens are spent on guidance the task never used.

   *Cost: no basis for prioritization or improvement.* Without the split between knowledge failures and logic failures, no team can say whether the above is getting better, and no investment in fixing it can be justified or ranked.

6. *Freshness is manual.* Whatever context a team has assembled goes stale on the product's next release. A platform team deprecates an API and publishes the replacement; the instruction file in a hundred repositories still describes the old one. The agent follows it confidently, and the change passes tests against a compatibility shim that is itself scheduled for removal. No signal tells the agent, or the developer, that the guidance is out of date.

   *Cost: stale guidance is followed with the same confidence as current guidance.* The failure is silent until review, and by then it has been multiplied across every repository that copied the same file.

Taken together, the firm is paying for the same knowledge to be sourced, assembled, transported, and re-verified per team and per harness, with the bill landing on senior reviewers, on token spend, and on Tech Risk, while having no measurement that would show whether any of it is working.
